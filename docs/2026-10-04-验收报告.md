## 八、晚间追加二（音质弹层「暂不支持」专项）

**问题**：QQ 歌曲的音质弹层里，192k/96k/48k AAC 三档被置灰标注「暂不支持」。原因是取流管线只实现了 FLAC/320/128 及一个内部名 m4a 的兜底前缀，弹层的 AAC 档位映射不到任何可请求的文件。

**修复（三档全部实装，含一处既有映射错误）**：
- 用 Meting provider 源码 + 实测文件大小双重校准了前缀映射：**C600=192k AAC、C400=96k AAC、C200=48k AAC**（`.m4a` 容器）。原代码把内部名 `m4a`(C400) 标注成 `size_48aac` 是错的，已修正为 `size_96aac`。
- 服务端 `getQQQualityCandidates`/`getQQFilename`/`getQQQuality` 增加三档（含降级链：192aac→96aac→128、96aac→128、48aac→96aac），`AUDIO_QUALITY_PREFERENCES` 白名单扩展。
- 前端 `AudioQualityPreference` 扩展三个 QQ 专属值（类型 + QQ 选项列表按码率降序排列 + 逐曲弹层映射）；非 QQ 平台写入/读取这些值会被守卫回落 auto。
- **实测验证**（本机 cookie 失效，用免费曲目匿名验证）：48aac→C200 下载长度 1,146,657B = `size_48aac` 精确相等；96aac→C400 = 2,293,231B = `size_96aac`；192aac 在无授权时正确降级到 96aac（有登录/会员时走 C600）。
- 弹层里仍置灰的只剩 **Hi-Res 无损 / 杜比全景声**：QQ 的 Hi-Res 前缀与杜比流是另一套体系（非 F000/C600 命名），本次未获可验证的前缀证据，保持诚实置灰。
- 新增 5 条单测（QQ 持久化、非 QQ 守卫、加载清洗、选项列表暴露）；全量 219 文件 / 2149+ 测试通过、构建成功。

> ⚠️ 生效方式：服务端改动需要重启应用内嵌的 local-server；前端改动经 `npm run build` 重建 dist 后由 dev:electron 的 preview 服务即时生效（本次已重建）。

## 八点半、晚间追加三（播放条视觉专项）

1. **音质按钮去图标、纯文字**：移除了耳机图标（`Headphones`），固定最小宽度（`min-w-[2.75rem]` 居中）——切换档位时按钮宽度不再变化。

3. **音质弹层闪现修复**：原来「点开先显示通用档位列表 → 拉到本曲详情后换成本曲列表」会闪一下。现在切歌即预取本曲 qualityLevels（30 分钟模块缓存 + 竞态守卫），弹层打开直接命中；首次未命中时只显示「自动 + 正在读取本曲可用档位…」加载态，不再出现列表替换。

## 十点、晚间追加九（无缝衔接的「智能短交叉」定稿）

用户定稿：交叉淡化设置与无缝衔接是两个独立功能；无缝衔接的交叉**必须是智能运算**——交叉时长、交叉位置、前后取量都由分析结果决定，不能是固定值。

- **复用现有 AutoMix 机制**（按用户要求核对后选定）：

- **无缝衔接自己的设计参数**（与 AutoMix 的区分）：窗口时长锁定在 **1.5–4s**（短交叉，不设 DJ 效果、不渲染、不做 stem）；窗口内的具体时长/起点/目标入点全部由规划器算出（节拍数 × 网格、目标跳过静音开头 `targetStartTime = introSilence`、源窗口落在有声内容尾部）。
- **实现**：
  - 新增 `prepareGaplessCrossfade()`：跨专辑且预加载就绪时分析两曲并生成计划（`id` 带 `gapless:` 前缀），以 armed 登记（`transitionStartTime` = 交叉起点，`transitionDebug` 供 HUD/节点取真实窗口）；
  - 播放到窗口起点 → `startTransition('beat-crossfade', plan)` 执行等功率交叉；计划带 `gapless:` 前缀**豁免**「按交叉设置收拢时长」的降级（否则智能窗口会退回固定 4s）；
  - 分析不可用/未就绪的兜底：2.5s 短窗 + 尾部静音裁剪（同样是计划对象，走同一执行链路）；

## 十二点半、追加十五（P0：过渡后歌词不跟屏 —— 根因定位、修复与实机验证）

用户复现：无缝/AutoMix 交叉期间旧歌词淡出、新歌词淡入与逐字**都正常**，**交接完成后**歌词列表不再跟随（高亮句不在视野里、列表停在切歌瞬间的位置）。

1. **根因（CDP 实机取证，非推测）**：
   - `LyricsDisplay` 的 `springWrapRef`（弹簧滚动轨道）与 `treeRef`（当前歌词树）挂在 `AnimatePresence` 里 `key=trackId` 的歌词树上，**新旧两棵歌词树共用同一组 ref**。切歌时新树先挂载（ref 指向新树），约 0.45s 后旧树退场被 React 移除 → React 回调 `ref(null)` 把**刚挂好的新树引用清成 null**。
   - 后果：弹簧滚动的 `measure()` 走 `if (!track) return` 静默失效 → 列表永久停在切歌瞬间的锚点，只有索引/逐字在推进（所以看上去"高亮句不知跑哪去了"）。
   - 证据链：React fiber 读取 `currentIndex=39`、`[data-index="39"]` 行 opacity=1（状态与渲染都正确），但弹簧 MotionValue 冻结在 index 0 的锚点（-1644.6）且 `isAnimating=false`；手动重新挂 ref + 触发一次测量后列表立即回到当前句（前后截图对比）。
   - **为什么"本来是没这个问题"**：柔和风格此前走原生滚动（`overflow-y-auto` + `scrollTo`，不依赖这两个 ref）；HEAD 中 `scrollStyleOfStyle` 已把「柔和并入弹簧滚动」（scroll 模式下 `isModernScroll` 恒 true），弹簧路径才让共用 ref 的这次误清成为致命伤。
2. **修复**：
   - `treeRef` / `springWrapRef` 改为「只接受非空元素」的稳定回调 ref —— 旧树退场的 `null` 误清被吞掉；测量侧再加 `data-wf-lyric-track` 标记 + 容器内取**最后一个**轨道兜底（AnimatePresence 渲染顺序：旧树在前、新树在后）。
   - `scrollLineToCenter` 作用域加 `isConnected` 判断（避免命中已卸载的旧树行）。
   - 提交帧落定：弹簧模式下不再调 `scrollLineToCenter`（容器是 `overflow-hidden` 的弹簧画布，原生 `scrollTo` 会与弹簧位移叠加 → 交接瞬间"整块歌词跳一下"），改为 `springAnchorTick` 触发一次重对锚。
   - 交叉淡化期间不再叠 10px 上浮：该分支此时被赋 `duration 0`，实际观感是「过渡窗口开启」与「视觉切换帧」各有一次**瞬移 10px**（用户反馈的边界位移来源之一）。
3. **实机验证（重建 dist + 重载渲染进程后，可信输入事件驱动）**：真实切歌（ストーリーテラー → ハイエナ - Hyena）后 —— `[data-wf-lyric-track]` 数量=1、宿主 ref 存活、滚动绑定同步；把弹簧扰动 500px 再强制一次测量 → 立即回到当前句锚点（backToAnchor=true）。旧构建在同样步骤下 ref 已为 null、测量静默失效。
4. 回归：`tsc --noEmit` 0 错误、219 文件 / 2148 测试通过、`npm run build` 成功（产物含 `data-wf-lyric-track` 标记）。
